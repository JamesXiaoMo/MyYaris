# 喜欢歌单元数据持久缓存与差分同步

2026-10-20。范围：后端维护一份有界持久元数据目录并做增删差分同步；iPhone 有同作用域的持久展示缓存；车机不新增缓存。本文只记录可复核的证据与边界，不含私人曲目、账号标识、凭据或部署地址。

## 1. 原因（证据）

- 部署的上游（NeteaseCloudMusicApi 容器 4.27.0）源码：`/playlist/track/all` 每次调用都先请求 `/api/v6/playlist/detail`（`n=100000`，返回整张歌单的有序 `trackIds` 与全部 `tracks`），再对当前分页切片请求一次 `/song/detail`。因此**每翻一页都重新下载整张歌单详情**。上游还对 GET 响应做 2 分钟 URL 级缓存，调用方必须带 `timestamp` 才能取到新数据。
- 对真实上游做的只读计数采样（747 首；未读取/打印任何曲目名、账号标识或凭据）：

| 上游调用 | 响应体 | 实测耗时 |
| --- | --- | --- |
| `/login/status` | 1.1 KB | 0.46 s |
| `/user/playlist`（含喜欢歌单版本提示） | 33 KB | 0.52–0.65 s |
| `/likelist`（无序 ID 集合，与 `trackIds` 集合一致） | 7.2 KB | 0.51–0.74 s |
| `/playlist/detail`（有序 ID + 全部元数据 + 权限） | 1.84 MB | 2.4–3.0 s |
| `/playlist/track/all` 一页 30 首 | 63 KB | 2.9 s |
| `/playlist/track/all` 一页 100 首 | 212 KB | 4.1 s |

  冷 `/music/queue` 旧实现串行取 8 页（每页 100）：按上表单页 2.9–4.1 s 估算约 25–33 s（估算值，未做端到端实测）。
- 其余原因：iOS 每次进入页面新建 controller 即取 30 首、dispose 即丢；手动刷新先清空旧列表；无上游版本/增量 API 可直接依赖；同作用域并发无合并；TTL 内 `trackCount` 缩小会出现 `offset` 空页但 `has_more=true`；上游请求中切 Owner 后旧页迟到仍可返回。
- 未发现下载全歌单音频、预取 CDN；封面为客户端异步图片加载，不阻塞列表。
- 上游可用的版本标识：`/user/playlist` 中喜欢歌单有 `trackUpdateTime`、`trackNumberUpdateTime`、`trackCount`。无写操作无法验证“重新点赞/排序”是否一定刷新它们，因此**只作为跳过重取的提示，不单独信任**：同时比较权威的 `/likelist` ID 集合，并按有界间隔强制完整复核。

## 2. 同步算法与边界

`FavoriteCatalog`（后端 `favorite_catalog.py`）：

1. **TTL 窗口**（`NETEASE_FAV_CHECK_TTL_SECONDS`，默认 60 s）：零上游调用。
2. **廉价门检**：Owner 严格校验（`/login/status` + `/user/playlist`，5 s 内刚做过则复用）+ 版本提示 + `/likelist` 集合。与目录一致 ⇒ 无变化，**不重取歌单详情**。
3. **完整取数**（首次 / 门检不一致 / 手动 `force` / 距上次完整校验超过 `NETEASE_FAV_FULL_RECHECK_SECONDS`，默认 6 h）：一次 `/playlist/detail` 同时得到有序 ID、元数据、权限；缺元数据的 ID 才补 `/song/detail`（≤100/批、有上限）；上游无法描述的 ID 记入 `skipped_ids`，不虚构。与上一 revision 做差集：新增 / 删除 / 重排 / 同 ID 元数据变化，有变化才**原子发布新的不可变 revision**（`max(旧+1, 毫秒时间)`，重启后仍单调）。封面只比较路径（上游会在 http/https 与 CDN 分片间摆动，不视为变化，已在真实采样中见到）。
4. **并发与保护**：同一时刻所有调用共享一次上游检查；`force` 至少间隔 15 s；检查期间会话变化（Cookie 保存/清除/账号切换）⇒ 丢弃结果、零写入；Owner 或歌单 ID 改变 ⇒ 废弃旧目录，不合并；网易云登出 ⇒ 清空内存与磁盘。
5. **读取**：已校验目录立即返回，过 TTL 则后台刷新（stale-while-revalidate）；显式喜欢点播/队列构建先检查（TTL 合并）。上游不可达时，仅对**已知同一 Owner**返回 `stale=true`；会话缺失/失效/Owner 无法证明一律 409，绝不以旧缓存冒充。`/login/status` 明确返回无会话现在映射为 409 鉴权失败（此前误归为 502 上游故障）。
6. **分页固定 revision**：首页返回 `revision`，后续以 `?revision=` 回传读取同一不可变版本；仅保留最近 3 个，丢失返回 409 `FAVORITE_REVISION_CONFLICT`，客户端从首页重来。
7. **存储边界**：只存白名单（id/title/artist/album/duration_ms/cover_url/fee/playable）、顺序、revision、etag、时间、Owner 不透明哈希键；不存音频、CDN/stream 地址、Cookie/Token。原子写（临时文件 + `os.replace`）、0600、≤5000 首/8 MB（超限仅驻内存，不截断）；重启恢复；损坏/篡改（etag）/schema 不符安全删除并重建。
8. **队列**：`init_favorite_queue` 以目录固定 revision 取页（内存切片），用目录自身 `total` 判断完整性（修复 `trackCount` 提示与真实列表不一致可能截断末页的风险）；新快照记录 `catalog_revision`。正在播放的活跃快照永不原地修改；显式 `?source=netease_favorite` 读取在目录有更新 revision 时生成新快照（新 `queue_version`），旧快照分页保持不可变；最多保留 6 个喜欢快照（活跃与待定快照受保护）。真实 heart/seed 校验仍走独立路径；播放 loop/shuffle、无自启、pending/applied、序号与心动失败保护未改动。

不是增量 API：上游无可靠增量接口，这里是“廉价门检 + 有界完整复核 + 差集发布”。同一 ID 的标题/封面/权限变化最长在完整复核间隔内（默认 6 h）或手动刷新时才会反映。

| 8 个并发检查（无变化） | 1 | 7.2 KB | 0.56 s |
| 25 页（每页 30）全部由内存提供 | 0 | — | 0.00 s |

持久文件 172 KB，不含 Cookie 文本。门检在 Owner 解析已过期时再加约 1 s（`/login/status` + `/user/playlist`）。
