# MyYaris 后端需求文档 V1.0

编制日期：2026-10-06（日本时间）  
部署设备：R9000P，Linux  
关联文档：`需求文档_V1.docx`

## 1. 目标与已确定方案

后端统一接收 Flutter 车机的中文语音、文字输入，以及 iPhone 快捷指令分享的地图链接或地址，解析为来源可靠的真实目的地，生成任务，下发给 Ottocast P3 Pro，并记录接收和打开 CAR NAVITIME 的回执。路线选择和开始导航由用户手动完成。

已确定：

- 车机前端使用 Flutter。
- 后端采用 Python FastAPI + SQLite，实际运行在 Linux R9000P 上。
- 外出的手机和车机通过 Tailscale 访问 R9000P；不采用 Cloudflare Workers 托管后端，也不采用 Cloudflare Tunnel 入口。
- iPhone 第一版使用分享快捷指令，不开发独立 iOS 应用。
- 后端构建委派给 Antigravity。SSH 连接方式和远端项目目录由用户在新窗口提供。

本文将已确定方案与建议默认值、待实测项目分别标注。与原文档冲突时，网络访问和部署架构以本文为准；原文档其余产品范围仍适用。

## 2. 范围和实施边界

第一版包括鉴权、地点解析、候选确认、语音转写适配、目的地任务持久化、长轮询、回执、离线恢复、过期与去重、部署和必要日志。

暂不包括校园入口视觉识别、自研地图或路线规划、无障碍自动点击开始导航、多用户商业平台。

当前本地 Flutter 项目已创建，已有目标设备安装和启动的代理执行记录；语音、后端通信、NAVITIME 跳转及后台运行兼容性尚未完成端到端验证。后端不能据此声称已具备导航能力。

## 3. 部署与网络

```text
iPhone 分享快捷指令 ─┐
                    ├─ Tailscale 私有网络 ─ R9000P（Linux）
Flutter / P3 Pro ────┘                      ├─ HTTPS 入口
                                           ├─ FastAPI
                                           ├─ SQLite
                                           └─ 语音 / AI / 地图适配
```

- 三端加入可互通的 Tailscale 网络，访问规则仅允许必要客户端访问后端服务。
- 优先使用固定的 Tailscale DNS 名称；实际地址、端口和 DNS 可用性在部署时验证。
- 对客户端提供统一 HTTPS 地址。Tailscale 组网本身不等于 HTTP 服务已配置 TLS；证书、HTTPS 终止方式及账户支持情况须实际检查后确定。
- 不依赖公网端口转发。不公开数据库、SSH 或 API 到公共互联网。
- 用 systemd 管理服务的开机启动和异常重启，以非 root 服务账户运行；安装服务和更改系统配置前确认用户授权范围。
- R9000P 须保持运行及联网。休眠或断网时，新请求明确失败；已持久化任务在恢复后按有效期处理。是否修改休眠配置由用户决定。
- 本机调试可先使用回环或明确限定范围的局域网地址，正式客户端接入仍以 Tailscale + HTTPS 为目标。

## 4. 内部结构

采用一个后端项目，按模块组织，不在第一版引入独立微服务。

| 模块 | 职责 |
| --- | --- |
| API 与鉴权 | 参数校验、调用方认证、资源权限、错误响应 |
| 地点解析 | 坐标、地图 URL、短链接、地址检索和候选生成 |
| 服务适配 | 语音识别、AI 理解、地图检索，支持替换供应商 |
| 任务管理 | 确认、排队、过期、替代、投递和回执 |
| 设备通信 | 长轮询、在线状态、重连与任务查询 |
| 持久化处理循环 | 执行解析工作、恢复未完成工作、清理临时音频 |

建议第一版运行一个 API worker。SQLite 是状态事实来源，内存通知仅用于唤醒等待请求；重启后从数据库恢复。未来增加进程或实例时，需另行设计共享通知和并发领取机制。

建议目录（实际远端根目录待用户指定）：

```text

  app/
    api/
    services/
    providers/
    repositories/
    schemas/
    config.py
    main.py
  migrations/
  tests/
  deploy/
  .env.example
  README.md
```

## 5. 输入解析与确认

两条输入流程共用解析模块：

1. 车机录音 → 转写 → 生成检索词 → 地点查询 → 车机确认 → 创建任务。
2. iPhone 分享 → 提取可靠目的地信息或地点查询 → 明确地点直接创建任务；歧义时返回候选，用户确认后创建任务。

规则：

- 明确经纬度须校验范围、坐标系及目的地含义；统一对外坐标契约，转换时保留原坐标系和来源。
- 地图 URL 不能把地图中心或路线起点当成目的地。
- 短链接仅受限跟随允许地图域名，解析失败时进入地点查询或返回可解释错误。
- 第一版优先适配 Google Maps 分享链接与普通地址文本，不承诺全部地图软件。
- 自然语言可结合客户端提供的当前位置和采集时间；位置缺失或陈旧时不假装拥有实时定位。
- AI 生成检索词并辅助选择查询候选，不生成未经检索的坐标。
- 多个合理结果返回简短候选列表；无匹配或描述不足返回澄清问题。
- 确认接口提交服务器生成的候选 ID，服务器重新验证所属请求和有效性，不信任客户端随意替换坐标。

## 6. 数据模型与状态

解析请求和车机任务分开保存，未确认候选不进入下发队列。

| 数据 | 主要字段 |
| --- | --- |
| 设备与凭据 | 设备 ID、客户端身份、令牌哈希、权限、启用状态、最近联系时间 |
| 解析请求 | 请求 ID、幂等编号、输入来源、原始输入、转写文字、当前位置及时间、解析状态、错误 |
| 地点候选 | 候选 ID、所属请求、名称、地址、经纬度、坐标系、来源、地点 ID |
| 下发任务 | 任务 ID、设备 ID、已确认地点快照、创建与过期时间、状态、投递尝试、确认期限、错误 |
| 回执与事件 | 任务 ID、事件编号、阶段、设备发生时间、服务器接收时间、错误码 |

建议解析状态：`resolving`、`needs_clarification`、`resolved`、`failed`。

任务状态：`queued`、`received`、`launch_requested`、`failed`、`expired`、`superseded`。

`launch_requested` 仅表示已调用系统打开请求，不代表目的地页面已核实或正在导航。回执必须单调更新，重复或迟到回执不能回退状态；冲突事件保留记录。

SQLite 文件放在 R9000P 本地固定数据目录，建议使用 WAL、短写事务及忙等待策略。数据库结构通过迁移管理。备份须使用能获得一致性快照的方法，不直接只复制活动 WAL 数据库的主文件。

## 7. API 契约

以下接口为建议初版，实现前统一字段和错误码：

| 方法与路径 | 功能 |
| --- | --- |
| `POST /voice` | 提交录音，持久化后返回解析请求 ID |
| `POST /destinations` | 提交文字、地图链接或坐标 |
| `GET /destinations/{id}` | 查询转写、解析状态、候选、澄清问题和任务关联 |
| `POST /destinations/{id}/confirm` | 确认候选并创建任务，重复确认返回已有结果 |
| `GET /devices/{id}/tasks/next` | 长轮询下一条有效任务 |
| `POST /tasks/{id}/ack` | 上报接收、打开请求或失败 |
| `GET /tasks/{id}` | 查询任务状态，供快捷指令与车机使用 |
| `GET /health` | 最小健康检查，不公开密钥或系统详情 |

- 手机令牌授权提交及查询自己的目的地；车机令牌仅授权领取和回报指定设备任务。
- 每个输入带唯一请求编号，按调用方和编号建立唯一约束；相同编号但不同内容应明确拒绝。
- 异步处理返回请求 ID 和可查询状态，不能把 HTTP 接收成功描述成导航打开成功。
- 统一时间采用 UTC 带时区格式，过期以服务器时间判断。
- 地点对象明确命名 `latitude`、`longitude`，避免坐标顺序混淆。
- 超时、无匹配、需要确认、鉴权失败、限流和供应商故障有稳定错误码及可理解说明。

## 8. 长轮询、离线与去重

- 沿用原文档的 HTTPS 长轮询，建议最长等待 20 秒，可配置。
- 无任务时结束等待，客户端再次请求；断线后指数退避并加入抖动。
- 一台设备同时只保留受控数量的待领取请求，避免重复等待导致多次并发投递。
- 投递保存尝试和确认期限，未收到回执时可重投递同一任务 ID。
- 车机持久化已处理任务 ID，避免重新打开；采取允许重投递、客户端去重的语义，不承诺跨崩溃的严格只执行一次。
- 创建新任务时在事务中替代旧的尚未执行任务；车机恢复上线只领取仍有效的最新任务。
- 已发起打开的历史任务不改写为待执行。已经投递的旧任务与新任务存在竞态，车机须在执行前检查最新状态/版本；已打开的 NAVITIME 无法由后台数据库操作撤回。
- 任务有效期、回执期限、重试次数、退避参数均可配置，具体默认值待确定。
- 在线状态基于最近有效联系推断，并标注时间，不把最近一次连接当成持续在线证明。

## 9. 语音、AI 与后台处理

- 录音格式、时长、大小限制与 Flutter 共同确定，不预设盒子已支持某种编码。
- 上传音频与解析请求持久化后再确认接收，避免服务重启丢失已接受的工作。
- 后台处理循环领取解析请求，分阶段记录进度，设置超时和受控重试；启动时检查中断请求，恢复或明确报告失败。
- 外部 API 的自动重试需考虑重复计费及结果不确定性。
- 临时音频采用可配置保留期限，处理后清理；默认不长期保存。
- 语音、AI、地图服务采用独立适配接口；供应商、价格和配额尚未确定。
- 是否本地运行模型须先检查 R9000P 的 CPU、GPU、显存及依赖条件，不预设已部署模型。

## 10. 安全、异常与运维

- 密钥只保存在后端，不写入 APK、快捷指令、日志或仓库。配置示例只放占位值。
- Tailscale 访问控制之外仍保留应用层鉴权；每个接口检查资源所属设备和调用方权限。
- 外部链接限制域名、重定向次数、响应大小及超时；每次跳转和实际解析地址均校验，阻止内网、回环和特殊地址访问。
- 对上传、解析调用和查询频率设置合理上限；日志不打印令牌或完整录音内容。
- 联网失败、语音无法识别、地图无匹配、供应商限流、数据库故障和任务过期均有明确状态。
- CAR NAVITIME 未安装、后台打开受阻由车机报告；不能由后端推定成功。
- 部署交付包括安装、配置、启动、停止、日志查看、备份、恢复和升级说明。
- 不在未授权情况下修改网络访问规则、休眠设置或其他已有服务。

## 11. 分阶段实施与验收

| 阶段 | 工作 | 验收条件 |
| --- | --- | --- |
| 1 | 远端环境检查、最小 FastAPI、鉴权、数据库迁移 | 在用户指定目录构建，可查询健康状态，密钥不入库 |
| 2 | 明确坐标提交、持久化任务、长轮询及回执 | Flutter 接收正确坐标，状态随真实回执更新 |
| 3 | 过期、替代、幂等、离线与重启恢复 | 重复提交不生成新任务；恢复不执行过期/旧任务 |
| 4 | Tailscale 和 HTTPS、Linux 服务管理 | 外出网络下手机及车机可访问；非授权身份被拒绝 |
| 5 | 分享链接及地址解析、候选确认 | Google Maps 分享无需重输；歧义不自动下发 |
| 6 | 中文文字理解、语音适配 | 来源明确的地点结果、可恢复处理和准确失败反馈 |

上述阶段顺序可按实际联网条件调整。阶段 2 的 NAVITIME 打开仍需车机实现配合，后端测试通过不代表全链路验收通过。

应有针对性验证：解析边界、资源权限、重复确认、并发任务替代、过期边界、回执丢失/乱序、服务重启恢复，以及实际移动网络连接。通过假供应商进行自动化测试，实际服务和实机结果另行记录。

## 13. Antigravity 启动前待补充

用户将在 Antigravity 新窗口提供：

1. SSH 主机、端口、用户名和允许的认证方式。
2. R9000P 上明确的项目目录。

到达远端后再检查 Linux 发行版、Python、现有项目、目录权限、Tailscale 状态和可用域名。不得猜测 SSH 信息、遍历尝试凭据、擅自选择远端项目路径或覆盖已有文件。

其余待定项：HTTPS 终止方式、服务监听地址、令牌初始化、供应商、任务有效期、录音约束及本地模型条件。可以先构建供应商可替换的骨架，不把尚未配置的能力显示为可用。
