## 四、 流媒体代理安全性与传输加固 (关键缺陷修复)

在此前运行中，流媒体代理存在以下潜在问题，本轮实施了专项彻底修复：

### 4.1 修复 1：新增 HTTP HEAD 探测支持 (消除 405 Method Not Allowed)
- **原因**：部分播放器（如 iOS AVPlayer、ExoPlayer 等）在请求大媒体文件前会先发送 `HEAD` 请求预检 `Content-Length` 与 `Accept-Ranges`。此前服务端路由仅绑定 `GET`，导致车机或探针收到 `405 Method Not Allowed` 并可能误判音频失效。
- **修复**：将 `/api/v1/music/netease/stream/{song_id}` 与 `/api/v1/music/stream/{track_id}` 均扩展为 `methods=["GET", "HEAD"]`，并在 HEAD 请求时返回完整的 200/206 头部（包含 `Accept-Ranges: bytes`、`Content-Length`、`Content-Type: audio/mpeg`）而无需拉取实体。
- **实测验证**：
  ```bash
  curl -I -k "https://myyaris.example.com/api/v1/music/netease/stream/1357375695"
  # 返回: HTTP/2 200, accept-ranges: bytes, content-length: 9584893, content-type: audio/mpeg
  ```

### 4.2 修复 2：真实音频 Magic Bytes 校验 (杜绝 200 HTML 伪装)
- **原因**：当网易云 CDN 遇到风控、Token 过期或版权下架时，可能返回 HTTP 200 但载荷为 `<!DOCTYPE html>` 或 JSON 错误；若代理盲目设置 `Content-Type: audio/mpeg` 返回，车机 ExoPlayer 解析非法音轨会直接抛出 `UnrecognizedInputFormatException` 崩溃。
- **修复**：在 `media_service.py` 中引入 `is_valid_audio_magic(chunk: bytes)` 检查器：
  - 严厉剔除 `<!doctype`, `<html`, `{"code"` 等伪装错误文本；
  - 严格校验 `ID3` (ID3v2)、`fLaC`、`OggS`、`RIFF`、`ftyp` (M4A) 及 raw MP3 frame sync (`0xFF 0xEx`)。
  - 首分块未命中 Magic Bytes 时直接返回 **502 Bad Gateway**，绝不把 HTML 假装成 MP3 发给播放器。
- **实测十六进制首字节**：
  ```
  00000000: 4944 3304 0000 0000 0023 5453 5345 0000  ID3......#TSSE..
  ```
  首字节为标准的 ID3v2.4 (`49 44 33 04`)，确认是纯正 MP3 音频。

### 4.3 修复 3：HTTP Range 206 分片与缓存写入原子性保障 (杜绝截断破损缓存)
- **分片拉取与断点续传**：实测 `Range: bytes=1000000-1004095`，服务端秒级返回 `HTTP/2 206 Partial Content`，`Content-Range: bytes 1000000-1004095/9584893`。
- **缓存写入原子性机制 (Atomicity Guarantee)**：
  - 边播边存 (`tee_stream_and_cache`) 或后台静默拉取 (`cache_track_background`) 时，首先写入临时文件 `netease_{song_id}.tmp`；
  - 首分块必须严格通过 `is_valid_audio_magic` 校验；
  - 只有当全量数据完整流式写入完毕且 `total_bytes > 0` 时，才执行 POSIX 系统级原子替换：`os.replace(tmp_path, final_path)`，并在同事务中将音轨持久化注册入 SQLite 数据库；
  - 若客户端中途拖动进度条断开、或网络发生丢包异常中断，系统在 `finally` 块中立即调用 `tmp_path.unlink(missing_ok=True)` 物理销毁临时文件，绝不向数据库写入任何脏索引，从根本上杜绝了部分截断破损文件被永久缓存在 SSD 中的隐患。
- **实测 Cache MISS 与 HIT 明确证据**：
  - **首次 MISS 证据**：
    ```http
    HTTP/2 200 OK
    accept-ranges: bytes
    content-type: audio/mpeg
    x-cache-status: MISS-CACHING
    content-length: 9584893
    ```
  - **二次 HIT 证据**：
    ```http
    HTTP/2 206 Partial Content
    accept-ranges: bytes
    content-type: audio/mpeg
    content-range: bytes 0-1023/9584893
    x-cache-status: HIT
    ```
    确认二次访问直接从宿主机 NVMe SSD 输出，零上游回源网络延迟。

### 4.4 修复 4：上游网易云搜索失败吞错修复 (杜绝以 HTTP 200 伪装空结果)
- **原因**：此前在 `netease_service.search` 与 `app/api/netease.py` 中，当上游 Netease API 出现网络超时、连接拒绝、HTTP 5xx 错误或业务错误返回时，代码使用全局 `try...except` 吞掉异常并直接返回 `{"total": 0, "songs": []}` 且 HTTP 200，导致前端误认为“当前搜索关键词在曲库中不存在”，严重误导用户与调试定位。
- **修复**：
  - 引入专有异常 `NeteaseUpstreamError(message, status_code)`；
  - 在 `search` 内部严格区分：
    1. 上游超时（`httpx.TimeoutException`）抛出 **HTTP 504 Gateway Timeout**；
    2. 上游返回非 200 状态码、网络连接异常或业务非 200 错误码，抛出 **HTTP 502 Bad Gateway**；
    3. 仅当上游正常返回 HTTP 200 且明确解析 `songCount: 0` 时，才向前端返回 HTTP 200 `{"total": 0, "songs": []}`。
- **自动化测试加固**：
  - `test_netease_search_legitimate_empty_results`: 验证合法空结果返回 200 空列表；
  - `test_netease_search_upstream_500_error`: 验证上游 500 报 502；
  - `test_netease_search_upstream_timeout`: 验证上游超时报 504；
  - `test_netease_search_upstream_business_error`: 验证业务非 200 报 502。
  - 实测全量测试通过。
