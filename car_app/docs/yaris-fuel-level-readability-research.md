# Yaris 混动油量证据与 OBD 扫描中断分析

> 下文保留修复前研究基线；后续收包日志与恢复实现见[传输修复说明](obd-transport-recovery.md)，安装与实车验收分别记录。

- 状态：2026-10-25 只读源码/用户提供报告分析及公开资料纠偏；未实现、构建、安装或进行实车操作。
- 源码基线：`d2cb8d0`；本次复核工作树 HEAD 为 `be85583`，相对该基线仅增加原研究文档。
- 目标：日本版 2022 Yaris Z 1.5 Hybrid。用户确认 Car Scanner 在连接配置 `Toyota Corolla Hybrid 2020-, RAV4 Hybrid 2019-, Camry Hybrid 2018-, Avalon Hybrid 2019-` 下能显示剩余燃油 L。具体传感器名称、内置 PID、公式及成功通信记录尚未取得。
- 本文仅公开脱敏统计、源码位置和研究结论。原始文件、车辆标识、CALID、原始响应及其可逆编码不随文档发布。

## 1. 当前可以确定的结论

1. 新报告不是完整扫描：固定 57 项候选实际执行 42 项，32 项匹配响应、22 项有标准值解析；9 项 `NO DATA`、1 项超时。结果为 `incomplete_transport`，剩余 15 项未测。不能计算全车支持率或把未测项归为不支持。
2. `7DF / 012F` 在本次条件下以 `NO DATA` 和提示符正常结束，耗时 260 ms；它不是本次扫描中断点，也不证明所有状态下均不支持。`012F` 的含义是液位百分比，不能直接提供升数。
3. 中断发生于 `7DF / 0904`：多个响应地址的多帧数据交错，1400 ms 内未收到提示符，尾部存在异常帧边界/序号。已知的是“主机没有收到完整结束”，尚不能确定缺字节发生于车辆、适配器、BLE、应用接收或文件转录层。
4. 随后的 `ATCAF1`、`ATSH7DF`、`ATH0` 都是 `unsynchronized_not_sent`，没有发送到适配器。最终 `restoration_acknowledged=false`、`polling_suspended=true`、应用连接状态仍为 true。这是停止后续写入的保护行为，不能写成“已恢复”或“蓝牙已经断开”。
5. `7C0 / 221022` 与 `7C0 / 2129` 不在当前候选列表，也没有在新报告中发送。当前源码还有独立的油量赋值和 UI 缺口；不能由本次扫描推导出 Car Scanner 使用哪个 PID。

## 3. 分层判断：已经看到什么，还缺什么

| 假设层 | 本次证据 | 尚不能认定的原因 / 最小新增证据 |
| --- | --- | --- |
| BLE 正常分片 | 接收器追加所有回调；正常多帧请求曾完成 | BLE 通知切开一行本来可以拼回。单凭半行不能称为应用按通知边界拼错。需要带单调时间和序号的回调字节记录。 |
| BLE/串口桥丢字节 | 尾部有短行、超长行、序号异常和截断 | 没有逐包/系统侧记录；不能确定损失发生在哪层，也不能量化丢包率。应用回调记录只能证明“交付给应用的字节”，不能独自证明空中链路丢包。 |
| 文本边界或转录损坏 | 某一声明地址后的行超过经典 CAN 8 数据字节；另一行呈现不连续 CF 序号 | 缺失 CR、头部或中段字节、适配器输出异常、转录改写均可能。不得补字节、猜分界再当原始证据。所供 JSON 另有一项 raw 字段为摘要而 trace 为原文，证据完整性须保留限制。 |
| 多 ECU ISO-TP/适配器时序 | 广播收到多个 First Frame；部分源有后续帧 | 多源流控、适配器串口输出及等待尾帧是候选原因。没有总线 FC/STmin/BlockSize 记录，也没有本次 CFC、ATST、ATAT 状态，不能认定流控关闭或 ECU 太慢。 |
| 主机截止时间过短 | 恰在固定 1400 ms 结束；没有提示符 | 没有首包、末包时间和完整迟到响应，不能证明延长即可成功。后续三个排空窗口也没有记录到提示符；“只差一点时间”没有证据。 |
| 解析器限制 | 超时拒收；地址猜测可能产生伪源，缺少逐行形状/错误层级 | 分类发生在交换结束之后，不控制当前等待提示符；修改解码不能让未收到的提示符出现。需要先解决可观测性，再按独立证据修正分类。 |

ELM 官方手册说明提示符代表可以接收下一条命令；CFC 流控与 CAF 格式化独立，ATH1 会使 CAF1 的接收显示保留类似原帧的字节。因此，看到 PCI 字节并不证明 CAF1 失效，CAF1 的 OK 也不证明 CFC1 已启用。适配器内部 ATST/自适应时序与应用 1400 ms 总截止时间必须分开看；兼容适配器的具体行为仍需验证。[ELM327DSL，印刷页 8-9、13-15、28-29](https://elmelectronics.com/wp-content/uploads/2020/05/ELM327DSL.pdf)

## 4. 油量数据链路与 Car Scanner 边界

| 层 | 当前源码事实 | 证据意义 |
| --- | --- | --- |
| 请求 | `car_obd_service.dart:1893` 含扫描 `012F`；`1914-1965` 没有 `7C0` 候选，后续私有探针本次未执行 | 常规轮询不请求油量；“从未请求油量”过于笼统，因为深扫确实请求过百分比。 |
| 换算 | 同文件 `738-754` 可解析 `012F` 百分比，`1797` 可生成扫描样例 | 解析帮助函数存在，不等于已接入日常遥测。 |
| 模型/赋值 | `obd_telemetry.dart:41-42` 定义两个油量字段；服务没有向 `fuelLevelLiters` / `fuelLevelPercent` 赋值 | 油量值未进入业务遥测。 |
| UI | `car_app/lib/ui/obd_dashboard_page.dart` 未读取上述字段 | 即使新增有效查询，也仍需独立接入展示与数据来源说明。 |
| 其他候选 | 服务 `1962-1963` 的 `7E0 / 222008` 标签为“累计燃油消耗总量” | 标签不是公开协议或本车验证，且累计消耗不能直接当剩余油量。 |

Car Scanner 官方更新记录包含用户所选配置名称；官方自定义传感器文档说明可设置请求、Header、公式，也可引用其他传感器。它们没有披露这个内置配置的剩余油量命令，不能证明该配置使用 `221022`、`2129` 或某个估算算法。[配置更新记录](https://www.carscanner.info/profile-database-changelog/)、[自定义传感器](https://www.carscanner.info/custompids/)

官方数据记录页确认 CSV/BRC 数值导出及相关依赖数据记录；数值记录不等于 AT/ECU 原始通信。该页不支持旧文关于必然可导出内置 PID、CSP 或固定名 `elm327.log` 的承诺。内置传感器详情是否展示 PID、当前版本是否能导出通信日志，应以实际功能为准；无法导出时仍应保留“未知”。[数据记录说明](https://www.carscanner.info/records/)

可区分的研究假设包括 ECU 返回以 L 为单位的数据、百分比乘容量、依赖其他传感器的计算、累计消耗扣减。后两类在该内置配置上的具体实现均未知。丰田官方只确认油箱容量参考值为 36 L；它不能证明 Car Scanner 的默认容量、ECU 标定算法或 PID。[丰田 Yaris HEV 维护数据](https://manual.toyota.jp/yaris/2207/hev/ja_JP/contents/vhch08se010401.php)

以下推论均撤回：

- 未修改容量却显示接近 36 L，不能“高度证明”原生升数；默认值、缓存、识别和计算链都未知。
- 某候选换算值与 Car Scanner 一致，只是相容证据；没有成功请求关联和公式证据，不能认定同一 PID。
- 两个候选 `NO DATA` 不证明 Car Scanner 在估算，也不证明所有会话/车型条件下都不支持。
- 相同平台、代际或社区条目不证明 ECU 地址、服务、初始化及公式通用；“ECU 以 L 返回”也不代表浮子/算法已经达到真实容积测量精度。

## 6. 最小可靠修复与复测建议（仅提案，待 root 审阅）

### 6.1 先补证据与离线验收

1. 设计私有 RX 记录：单调时间、事务 ID、通知序号、长度、原始字节、实际 MTU、写入开始/完成、首/末通知、提示符及总截止时刻。记录实际 ACK 的协议、格式、Header、过滤器、流控和时序状态；不能把适配器默认值当已观测值。不能读取原态的设置保持 unknown，避免盲目更改。
2. 保留超时之后的完整排空字节与终态快照：当前 `late_reply_drain` 只在迟到 `>` 时入报告；无提示符的新增碎片在结束时未必独立归档。把“排空等待”和“确实发送/收到 ACK”分开计时与标记。
3. 用脱敏合成数据离线验证：任意 BLE 切片应逐字节重建同一流；覆盖提示符单独成包、CR/LF 跨包、多 ECU 交错、CF 缺失/乱序/重复、超长/短行、旧响应尾部、提示符后残留、取消及断连。损坏输入不得靠猜测修复成有效数据；暂不扩展探针。
4. 后续若修改解析器，应保留外层 `completion=timeout`，同时记录内部帧的长度/序号错误与位置；将地址形状和验证过的响应源分开。解析分类不是 ISO-TP 总线流控实现。

### 6.2 单次受控复测的依赖与判据

仅在后续单独授权、停车且适配器由一个客户端独占时执行；本研究没有发送下列任何请求。

- 优先验证短响应与取消/迟到提示符恢复。接着针对已经观测过的一个排放响应源做定点 `0904`，只改变寻址范围，保持其他设置可追溯；不要直接重跑 57 项或扩大 ECU 搜索。源地址与物理请求映射仍需核实。
- 比较同适配器同状态下 Car Scanner 的成功流与应用流；先取得实际传感器名、单位、设置和版本。若其 UI 不暴露内置 PID，则寻找当前版本实际可用的通信证据，不能承诺固定菜单/文件名。一次数值相同不能锁定请求来源。
- 时间策略须由逐包证据决定：只有持续收到结构合法的后续帧且晚到提示符最终可验证，才考虑受总上限约束的活动等待；同步等待与诊断成功分类分开。字节已经缺失、行超长或序号断裂时，延长 timeout 不能使结果有效。
- 无提示符时保持隔离与暂停，不连续尝试恢复写入。任何中断/重新握手都应有明确策略、独占权和恢复证据；不自动 `ATZ`、重置或发空 CR（空 CR 在空闲时可能重复上一条请求）。
- 恢复实际 ACK 观察过的原状态，而非固定 `ATH0`/广播 Header。原 Header 本次为 unknown，广播 fallback 即便得到 ACK 也只能叫“显式 fallback”，不能叫原状态恢复；缺少必要恢复 ACK 时保持暂停并显示原因。
- 传输与恢复通过后，另开最小油量定点复核；优先按成功对照确定精确请求，社区 `7C0` 候选仍属待测。不要让可选 Mode 09 元数据成为油量专项验证的必经步骤。

验收必须分别报告：传输是否完整、响应是否匹配且长度有效、工程值/来源是否验证、原状态是否恢复、轮询是否安全恢复。后续油量显示需区分 ECU 返回 L、液位 %、明确标注的估算和 unknown；未接入不是 0。

## 7. 本次纠偏范围与状态

本文替换旧版中关于精确 Car Scanner PID、平台通用性、默认容量、通用 `2129` 倍率及“数值一致/两个 NO DATA 即定性”的过度推论，撤下自动复位和固定 15 条恢复序列。历史总数与新报告分开；新报告仅支持本次 `012F NO DATA`，不扩大到所有工况。

业务源码、探针、应用配置和车辆均未改动；本次没有执行 Flutter 测试、构建、安装、扫描、AT/PID、播放或导航。当前仅完成研究与文档纠偏，修复和实车验收仍未实施。
